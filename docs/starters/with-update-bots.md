# Starter kit: Evergreen alongside Renovate and Dependabot

Most repositories already run an update bot. Renovate and Dependabot keep dependencies moving and open security updates; neither knows whether a package is deprecated, retired, or past its support window. Evergreen adds that lifecycle layer, and it prints configuration for both bots so their next pull requests start from the findings in this repository.

Both generators scan the repository offline and print to stdout. Neither edits a config file, and the scan makes no network requests.

## What each tool reports

| | Renovate | Dependabot | Evergreen |
|---|---|---|---|
| Keeps dependencies current | yes, from its config and schedule | yes, weekly or daily per ecosystem and directory | no; it reports, it does not update |
| Security updates | yes | yes | names affected versions and, where bundled data has them, advisory ids |
| Lifecycle status | only what its config tells it | no | deprecated, end-of-support, end-of-life, removed, or scheduled, per rule |
| Evidence | release notes it can read | changelog links it finds | rule id, authoritative source URL, deadline, severity, exact location |
| Replacement | applies a `replacementName` you configure | no | names the replacement in the finding, and `evergreen context` builds migration steps |
| Runtime pins | `allowedVersions` you configure | no equivalent | Node.js and Python end-of-life findings |

The bots decide *when* to change a version. Evergreen decides *whether the current one is still supported* and what to say about it. Run them together rather than choosing one.

## Sample repository

The outputs below come from a small sample repository:

```json
{
  "name": "update-bots-sample",
  "private": true,
  "dependencies": { "request": "^2.88.2", "node-sass": "^9.0.0" },
  "engines": { "node": ">=18" }
}
```

with `18` in `.nvmrc` and `actions/checkout@v2` in `.github/workflows/ci.yml`. Both commands were run from that directory; the results are deterministic, so the same repository always prints the same fragments.

## Generate both fragments

From the repository root:

```bash
npx evergreen-deprecation renovate-preset . > renovate-fragment.json
npx evergreen-deprecation dependabot-config . > dependabot-fragment.yml
```

### Renovate fragment

```json
{
  "$schema": "https://docs.renovatebot.com/renovate-schema.json",
  "description": "Generated by Evergreen from repository lifecycle findings. Review before merging into renovate.json; Evergreen does not edit config files.",
  "packageRules": [
    {
      "description": "Evergreen: keep Node.js on a supported release (nodejs.runtime.eol-18)",
      "matchDatasources": ["node-version"],
      "matchPackageNames": ["node"],
      "allowedVersions": ">=22"
    },
    {
      "description": "Evergreen: replace node-sass (npm.package.node-sass.eol)",
      "matchDatasources": ["npm"],
      "matchPackageNames": ["node-sass"],
      "replacementName": "sass"
    }
  ]
}
```

- A finding whose replacement is itself a package name becomes a `replacementName` rule. Prose replacements, such as `request`'s "Native fetch or a maintained HTTP client", are skipped because Renovate cannot apply them.
- Node.js and Python runtime findings become `allowedVersions` pins, so Renovate stays on a supported line instead of offering the next unsupported one.

### Dependabot fragment

```yaml
# Generated by Evergreen from repository lifecycle findings.
# Review before merging into .github/dependabot.yml; Evergreen does not edit files.
version: 2
updates:
  - package-ecosystem: github-actions
    directory: "/"
    schedule:
      interval: weekly
    groups:
      evergreen-deprecated-packages:
        applies-to: version-updates
        patterns:
          - "actions/checkout"
  - package-ecosystem: npm
    directory: "/"
    schedule:
      interval: weekly
    groups:
      evergreen-deprecated-packages:
        applies-to: version-updates
        patterns:
          - "node-sass"
          - "request"
```

- Each ecosystem and directory with findings gets a weekly entry whose `groups.patterns` list the affected packages, so their updates arrive in one reviewable pull request per directory instead of several.
- Workflow findings always point at `/`, where Dependabot looks for `.github/workflows` itself. Runtime findings have no Dependabot equivalent and are skipped.
- An empty scan prints comments only, never `updates: []`, which Dependabot rejects.

## Set up Renovate

Merge the printed `packageRules` into the `packageRules` array in `renovate.json` and keep the rest of your config:

```json
{
  "$schema": "https://docs.renovatebot.com/renovate-schema.json",
  "extends": ["config:recommended"],
  "packageRules": [
    {
      "description": "Evergreen: replace node-sass (npm.package.node-sass.eol)",
      "matchDatasources": ["npm"],
      "matchPackageNames": ["node-sass"],
      "replacementName": "sass"
    }
  ]
}
```

Validate before committing:

```bash
npx --yes --package renovate -- renovate-config-validator renovate.json
```

Renovate now retargets `node-sass` updates to `sass` and keeps the `node-version` datasource on 22 or later. It still decides when to open the pull request and how to group it. More detail: [Feeding Renovate](../ADOPTION.md#feeding-renovate).

## Set up Dependabot

Merge the printed `updates` entries into `.github/dependabot.yml`. Keep any entries you already have; do not duplicate an ecosystem and directory that is already listed.

```yaml
version: 2
updates:
  - package-ecosystem: npm
    directory: "/"
    schedule:
      interval: weekly
    groups:
      evergreen-deprecated-packages:
        applies-to: version-updates
        patterns:
          - "node-sass"
          - "request"
```

The grouping is the point: Dependabot already updates those packages, and the group makes the deprecated ones land together so the migration is reviewed as one change. Dependabot does not replace `node-sass` with `sass` and has no runtime pin; those two parts come from Evergreen's findings and the Renovate fragment. More detail: [Feeding Dependabot](../ADOPTION.md#feeding-dependabot).

## Keep the lifecycle gate in CI

Config fragments tell the bots what to do after a finding exists. The CI gate is what notices new findings, including usage that a bot pull request introduces. Copy the workflow from the [Next.js starter](nextjs.md#1-pull-request-workflow):

```yaml
- uses: arminazimi/evergreen@v0.7.1
  with:
    baseline: .evergreen-baseline.json
    fail-on-severity: high
```

Accepted findings go in the baseline, new ones fail the pull request, and the failure names the rule, source, deadline, and file. See [GITHUB_ACTION.md](../GITHUB_ACTION.md) for inputs and SARIF upload.

## Keep the fragments current

The fragments are a snapshot of one scan. Regenerate them after a migration lands or dependency policy changes, review the diff, and delete rules that no longer apply:

```bash
npx evergreen-deprecation renovate-preset . > renovate-fragment.json
npx evergreen-deprecation dependabot-config . > dependabot-fragment.yml
```

Because the output is deterministic, a diff shows exactly which findings appeared or disappeared. Commit only the rules you merge into the real config; the generated files themselves can stay out of the repository.

## What Evergreen does not do

The scan reads repository files and bundled lifecycle data only. It never evaluates repository code, never uses the network, never edits bot configuration, and never runs a migration command; it prints suggestions, and the verification commands in a migration packet are for a person or agent to run deliberately. Rules and their sources are reviewed data; see [Lifecycle rules](../RULES.md).
